# دورة تدوير مفاتيح Supabase — بطاقة P2 (البند 14 / F-15)

> آخر تحديث: 2026-11-09 · المراجعة الدورية: سنوياً (تلقائياً عبر `key-rotation-reminder.yml`)
> **الموعد النهائي: تدوير مفتاح anon الحالي قبل 3 نوفمبر 2036**

## 1) خريطة المفاتيح — ما هو سرّ وما هو عام؟

| المفتاح | متغير البناء | التصنيف | موضع الاستخدام |
|---|---|---|---|
| anon / publishable | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | **عام بالتصميم** — آمن للمتصفح، الحماية عبر RLS | `src/lib/supabase.ts` → `createClient` |
| service_role | — (متغير خادمي فقط، إن لزم) | **سرّ مطلق — لا يوضع أبداً في المستودع أو متغيرات `NEXT_PUBLIC_*`** | لا يستخدمه الموقع حالياً |
| Google Client ID | `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | عام (مُعرِّف لا سرّ) | زر "المتابعة بحساب Google" |

مبدأ ثابت: أي قيمة تبدأ بـ `NEXT_PUBLIC_` تُخبز في حزمة المتصفح عند البناء، فيجب أن تكون
قابلة للنشر علناً. الحماية الحقيقية للبيانات هي **سياسات RLS** في
`supabase/schema.sql` + `supabase/migration-002.sql`، وتُثبت دورياً بسكربت
`supabase/verify-rls.sql` (5 اختبارات تمنع عميل anon من القراءة/الكتابة غير المصرّحة).

## 2) لماذا نُدوّر مفتاحاً عاماً أصلاً؟

- مفتاح anon بصيغة JWT القديمة يحمل تاريخ انتهاء افتراضياً (**نوفمبر 2036** لهذا المشروع)؛
  تدويره يقطع أي استخدام مفرط أو خارج نطاق إن تراكم.
- تدوير دوري يضمن أن أي نسخة مسربة في بيئة سابقة أو جهاز موظف سابق تصبح عديمة القيمة.
- Supabase يوفّر الجيل الأحدث `sb_publishable_…` / `sb_secret_…` الذي يفصل دور الحزمة عن
  التواقيع — الترحيل إليه عند توفره في واجهة المشروع هو البديل المفضّل طويل الأمد.

## 3) إجراء التدوير (خطوة بخطوة)

1. **في Supabase Dashboard** → Project Settings → API:
   - اضغط **Rotate JWT secret** (أو أنشئ publishable key جديدة عند الترحيل للجيل الجديد).
   - انسخ المفتاح الجديد فوراً — القديم يُبطل بعد فترة انتقال قصيرة (Grace period).
2. **أطلق مستند الحوادث**: سجّل التاريخ، سبب التدوير، والقيمة الجديدة في مدير أسرار
   الفريق (لا في المستودع).
3. **أعد بناء النسخة الثابتة بالمفتاح الجديد** — المفتاح مُخبز في حزمة المتصفح عند البناء:
   ```bash
   NEXT_PUBLIC_SUPABASE_URL=… NEXT_PUBLIC_SUPABASE_ANON_KEY=<الجديد> \
   bash scripts/build-static.sh
   ```
   ثم انشر `out/` إلى فرع `published-site` كما في دورة النشر المعتادة.
4. **أعلن إعادة تسجيل الدخول**: تدوير JWT secret يُبطل جلسات المستخدمين الحالية
   (كل توكن مستخدم موقّع بالمفتاح القديم). الجلسات تتجدد تلقائياً بعد دخول جديد؛
   سلة المشتريات والمفضلة في `zustand` لا تتأثر.
5. **تحقق بعد التدوير** (معيار القبول):
   - [ ] الموقع يجلب البيانات ويسمح بتسجيل الدخول من المتصفح.
   - [ ] `supabase/verify-rls.sql` يمر بـ 5/5 (RLS ما زال يمنع anon).
   - [ ] أي استخدام للمفتاح القديم يعطي `401/403` في السجلات.
   - [ ] تحديث هذه الوثيقة بتاريخ التدوير الجديد والموعد التالي.

## 4) الجدولة والتذكير

| البند | القيمة |
|---|---|
| مراجعة سنوية مجدولة | 1 يناير من كل عام — سير عمل `key-rotation-reminder.yml` يفتح مسألة تذكير في المستودع تلقائياً |
| تدوير فعلي | كل 24 شهراً أو عند تسريب مشتبه به، أيهما أسبق |
|  **الحد النهائي لهذا المفتاح** | **قبل 3 نوفمبر 2036** (انتهاء صلاحية JWT الموثق فعلياً عند فك الترميز — iat 2026-11-04 / exp 2036-11-03) |
| مسؤول التنفيذ | مالك المشروع (CTO-DRS) |

> إن لم يُنفَّذ التدوير قبل الحد النهائي سيعمل الموقع حتى انتهاء الصلاحية ثم يفشل
> كل نداء Supabase — لذا التذكير المجدول إلزامي وليس تحسين اختياري.
